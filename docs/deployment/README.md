AMP — Deployment Documentation

1. Overview

This document describes the deployment requirements and operational
procedure for the AMP (Access Management Portal).

AMP is deployed as a React/Vite frontend with an Express/TypeScript
backend and MySQL database.

Production deployment should use environment-specific configuration,
controlled database migrations, secure secrets management and validated
build artifacts.

4. Prerequisites

A deployment environment should provide:

Node.js compatible with the project

npm

MySQL/MariaDB-compatible database

network access between application and database

required environment variables

access to the application repository or release artifact

The deployment environment should use a supported production Node.js
release and should keep development-only tooling out of the runtime
environment where practical.

5. Source Checkout

Clone or update the required branch/release in the deployment
environment.

Example:

git clone <repository-url>
cd amp
git checkout security-hardening

For production, deployment should preferably be based on a reviewed,
known commit rather than an unreviewed working tree.

6. Install Dependencies

Use the lockfile for deterministic dependency installation.

npm ci

Do not replace npm ci with an unpinned dependency installation during
production deployment.

8. Database Preparation

Before starting the application:

confirm database connectivity

confirm the target database exists

apply pending migrations

verify required tables/indexes

verify backup/recovery readiness

Migration command currently exposed by the project:

npm run db:migrate

Database migration files belong under:

database/migrations/

Production migrations should be reviewed before execution.

9. Production Validation Before Deployment

Run the complete validation pipeline:

npm ci
npm run lint
npm test
npm run build
npm audit

Expected conditions:

lint -> success
tests -> all passing
build -> successful
audit -> no unacceptable vulnerabilities

A deployment should not proceed when security-critical validation fails.

10. Build Process

The production build is generated by:

npm run build

This performs:

Vite frontend build +
esbuild backend bundle
=
dist/

Expected runtime artifacts include:

dist/
├── index.html
├── assets/
└── server.cjs

The build may emit performance warnings such as large JavaScript chunks.
Such warnings should be reviewed separately from actual build failures.

11. Application Startup

The production application is started using:

npm start

The start script executes:

node dist/server.cjs

Development mode remains:

npm run dev

Development mode should not be used as the production service process.

12. Health Verification

After startup, verify the application health endpoint.

Expected endpoint:

/api/health

Verify:

server responds

API routing is available

database connectivity is reported correctly

no startup configuration errors are present

A successful HTTP response alone is not sufficient if the application
reports that its required database connection is unavailable.

13. Network Configuration

The application may be deployed behind:

a reverse proxy

an institutional web server

a secure internal network

a cloud load balancer

Production network configuration should restrict exposure to the
required ports and trusted client networks.

Where HTTPS is used, terminate TLS at the approved infrastructure layer
and forward traffic to the application securely.

14. Reverse Proxy

A production reverse proxy may provide:

TLS termination

hostname routing

HTTP-to-HTTPS redirect

request size limits

connection controls

security headers

access logging

The proxy must forward API requests correctly to the Express backend.

Static frontend assets may be served either by the application or by the
approved web server/reverse proxy according to the deployment design.

15. CORS

Production CORS configuration should allow only the intended frontend
origin(s).

Do not use unrestricted wildcard origins for authenticated production
APIs unless there is a documented security reason and compensating
controls.

The configured client URL should match the actual deployed frontend
origin.

16. Secrets and Credentials

Production secrets must be stored using secure environment or secret
management facilities.

Examples:

DB_PASSWORD
JWT_SECRET
MAIL_PASSWORD

Do not store these values in:

.env committed to Git
source files
README files
test files
frontend code
browser local storage
CI logs

A safe .env.example may document variable names without real secrets.

17. Database Backup

Before production schema changes:

verify that a current database backup exists

verify backup accessibility

record the planned migration

apply migration

verify application behavior

A restoration procedure should be tested periodically.

Production backups may contain sensitive personnel information and must
therefore be protected with appropriate access controls.

20. Database Connectivity

The application database layer performs a connection test during server
initialization/health verification.

The application should remain explicit about database availability.

A production deployment must not silently operate as a fully functional
application when its required persistent database is unavailable.

21. Process Management

The Express production server should run under an approved process
manager or service supervisor appropriate to the deployment environment.

Examples may include:

Windows Service
systemd
PM2
container orchestration
institutional application service

The process manager should provide:

automatic restart

controlled shutdown

log capture

service status

startup configuration

22. Logging

Production logs should capture useful operational information without
exposing secrets or sensitive personal information.

Log:

startup/shutdown events

database connectivity errors

application errors

relevant API failures

security/audit events where appropriate

Do not log:

passwords

JWT secrets

database passwords

complete sensitive financial details

unnecessary personal data

23. Monitoring

Production monitoring should cover:

application availability

API response failures

database connectivity

process health

disk/storage usage

CPU/memory usage

authentication failures

security events

workflow processing failures

Thresholds should be defined according to the deployment environment.

24. Rollback

A rollback plan should exist before production deployment.

Application rollback:

Current Release
|
v
Restore previous known-good application version

Database rollback depends on the migration design.

Where destructive migrations are involved, the deployment plan should
include an explicit recovery strategy before executing the change.

25. Zero-Downtime Considerations

For a single-server deployment, a short restart window may be acceptable
depending on operational requirements.

For higher availability deployments:

use multiple application instances

use a reverse proxy/load balancer

use compatible migration sequencing

perform health checks before routing traffic

The exact strategy depends on institutional infrastructure.

26. File and Permission Security

Production application files should be writable only where required.

Recommended principles:

application source should not be writable by the runtime user

logs should use controlled permissions

uploaded files should be stored outside executable paths where possible

configuration files containing secrets should be restricted

backups should be protected

27. Update Procedure

For a routine update:

1. Review changes
2. Backup database
3. Pull reviewed commit
4. npm ci
5. npm run lint
6. npm test
7. npm run build
8. Apply required migrations
9. Restart application
10. Check /api/health
11. Perform smoke tests
12. Review logs

13. CI/CD Relationship

GitHub Actions performs pre-deployment validation through:

ci.yml
security.yml

CI validates:

npm ci
npm run lint
npm test
npm run build

Security validation includes:

npm audit --audit-level=high

The production environment should consume a validated commit/artifact,
rather than bypassing the CI/security checks.

29. Deployment Security Checklist

Before production release:

Production secrets are external to Git.

Database credentials are valid and least-privileged.

Database backup is available.

Required migrations are reviewed.

npm ci succeeds.

npm run lint succeeds.

npm test succeeds.

npm run build succeeds.

npm audit is reviewed.

HTTPS/network controls are configured.

CORS is restricted appropriately.

Health endpoint responds.

Authentication works.

Authorization restrictions work.

Critical workflow smoke tests pass.

Logs do not expose secrets.

Rollback procedure is understood.

30. Environment Separation

Development, testing and production environments should be separated.

Each environment should have its own:

database
secrets
URLs
mail configuration
logging configuration
operational access

Production data should not be copied into development/test environments
without an approved data-protection process.

31. Operational Ownership

Deployment responsibilities should be clearly assigned for:

application releases

database migrations

server/process management

backups

secrets

monitoring

security incidents

rollback

Operational ownership depends on the hosting/institutional environment.
